# Job Fair Tracker — Developer Reference

> **Purpose:** PwD (Persons with Disability) hiring job fair candidate tracker.
> Organises candidates from multiple Excel response sheets into a per-company, per-JD dashboard with Green / Yellow / Red screening zones, CV upload pool, shortlisting, and per-company Excel exports.

## 1. Architecture at a Glance

```
Excel sheets (raw data)
       │
       ▼
scripts/ingest.py  (Python, run once to refresh)
       │  reads MASTER sheet for JD list
       │  reads candidate response sheets
       │  scores, deduplicates, matches pool candidates
       ▼
data/data.json     (static JSON, ~1 MB)
       │
       ▼
server.js          (tiny Node HTTP server, dev only)
  GET /api/data  → serves data.json (with optional password check)
  GET /*         → serves public/
       │
       ▼
public/index.html  (single-file SPA, vanilla JS + CSS)
  - All routing, rendering, scoring adjustments, CV matching,
    pool upload, shortlisting, and Excel downloads run in the browser.
```

**There is no database.** All HR edits (zone overrides, shortlists, notes) live in the viewer's `localStorage` only — they are **not shared** between users.

## 3. Data Pipeline — `scripts/ingest.py`

Run: `python3 scripts/ingest.py` (requires `pandas`, `openpyxl`)

### 3a. JD Loading
- Reads `MASTER["JDs Overview "]` (note trailing space in sheet name).
- Each row: Company Name, JD title (may be a `=HYPERLINK(url, text)` formula), Job Type (`ty`), Experience (`e`), Location (`l`).
- Strips file extensions and "JD -" prefixes from titles.
- Builds two lists: `cos` (company names) and `jds` (JD dicts).
- Appends a sentinel company `"Other roles (not in your JD sheet)"` at index `OTH` for unmatched candidates.

### 3b. Candidate Sheet Sources (`SRC` list)
Each entry is `(file, sheet_name, companies_or_label, role_column, default_role)`:
- `companies_or_label`: list of company names (from `cos`) → matched to JDs of those companies. If a string → freeform "other" label, all candidates go to one catch-all JD.
- Role matching uses Jaccard-similarity tokenisation; threshold ≥ 0.6 for a match.

### 3c. Talent Pool Sources (`POOL` list)
Candidates in the Naukri / Shortlist / Purchase-Executive files have **no applied JD**. They are matched to every JD that scores ≥ `YELLOW` (52) across all companies, capped at 5 best matches per person. Those with zero matches land in `"Talent pool: no matching JD yet"`.

### 3d. Deduplication
Key = `(email_or_phone_or_name.lower(), jid)`. Priority: explicit form application beats pool match; then latest timestamp; then higher score.

### 3e. Output (`data/data.json`)
`json.dump(dict(cos, jds, people, pl, thr), ...)` — see §4.

### 3f. Field Extraction (`F` dict + `load()`)
Column headers are matched via regex patterns (case-insensitive). Key fields:
`name`, `em` (email), `ph` (phone, normalised to last 10 digits), `exp`, `loc`, `sk` (skills), `q` (qualification), `org`, `des` (designation), `cv` (first https URL in CV column), `ct` (current CTC), `ex` (expected CTC), `np` (notice period), `dt` (disability type), `dp` (disability %, normalised), `ad` (address), `ts` (timestamp).

## 4. `data/data.json` Schema

```jsonc
{
  "cos": ["Wipro", "Dell", ...],          // company names; index = company id
  "jds": [
    {
      "id": 0,                            // index into this array
      "c": 2,                             // index into cos[]
      "t": "Content Moderator",           // JD title
      "ty": "Non-Tech",                   // job type
      "e": "0-2 years",                   // experience requirement string
      "l": "Bengaluru",                   // location
      "u": "https://drive.google.com/..." // JD file URL (may be "")
    }, ...
  ],
  "people": [
    {
      "n": "Jane Doe",
      "org": "Acme Corp",
      "e": "3 years",         // raw experience string
      "loc": "Bengaluru",
      "np": "30 days",
      "em": "jane@example.com",
      "ph": "9876543210",
      "cv": "https://drive.google.com/...",
      "sk": "Python, SQL",
      "q": "B.Tech",
      "ct": "4 LPA",
      "ex": "6 LPA",
      "ts": "2026-07-28",
      "src": "Wipro (COntent) First source Cu",  // source sheet name
      "role": "Content Moderator",               // role text from form
      "note": "",
      "dt": "Locomotor",      // disability type
      "dp": "45%",            // disability percentage
      "ad": "123 Main St...",
      "pr": "Yes"             // preferred relocation / willing to relocate
    }, ...
  ],
  "pl": [
    [jid, pid, score, reason_string, is_pool_flag],
    ...
  ],
  // pl is sorted by (jid, -score)
  "thr": [66, 52]             // [GREEN threshold, YELLOW threshold]
}
```

`pl` is the placement list: each row links one person (by `people` index) to one JD (by `jds` index) with score and reason. One person can appear in multiple `pl` rows (one per matched JD).

## 5. Front-end — `public/index.html`

Single-file SPA. No build step. All CSS, JS, routing, and rendering in one file (~1500 lines post-edits).

### 5a. Startup
```js
(async () => {
  start(await api(sessionPassword));  // fetches /api/data
})();

function start(d) {
  D = d;                  // global data object (cos, jds, people, pl, thr)
  rebuildCandidateList(); // builds C[] from D.pl + S.pool (localStorage pool)
  render();
}
```

### 5b. Global Variables
| Variable | Type | Purpose |
|---|---|---|
| `D` | Object | The full `data.json` payload |
| `C` | Array | Flat candidate list built from `D.pl` + `S.pool`; each item has all people fields plus `id`, `jd`, `co`, `sc`, `rs`, `pool` |
| `S` | Object | localStorage state: `ov` (overrides), `log` (change log), `sl` (shortlist), `qe` (custom questions), `pool` (uploaded pool candidates) |

### 5c. Candidate Object (in `C[]`)
```js
{
  id: "p42",          // "p" + index for form candidates; "pool_N" for pool uploads
  jd: 7,              // JD index (may be null for unmatched)
  co: 2,              // company index
  sc: 78,             // raw score from data.json
  rs: "3 yrs experience; ...",  // raw reason string
  pool: false,        // true = talent pool or uploaded pool
  n, org, e, loc, np, em, ph, cv, sk, q, ct, ex, ts, src, role, note, dt, dp, ad, pr
  // all people fields from data.json
}
```

### 5d. Hash Router
```
#/            → vHome()         companies grid
#/c/{i}       → vCo(i)          company JD list
#/j/{id}      → vJd(id)         JD candidates (zones / sheet / questions tabs)
#/u           → vUn()           unassigned candidates
#/multi       → vMulti()        candidates matching 2+ JDs
#/shortlist   → vShortlist()    per-company shortlist view
#/cv          → vCvMatch()      CV upload & JD matching
#/pool        → vPoolUpload()   Excel/Google Sheet pool upload
```

### 5e. Key Functions Reference

**Scoring / Zone:**
- `ai(c, j)` — computes adjusted score for candidate `c` against JD `j`; applies disability and experience penalties on top of raw score
- `zone(c, j)` — returns `'g'`/`'y'`/`'r'`; respects user overrides in `S.ov`
- `disCheck(c)` — checks disability type present and % ≥ 40; returns `{ok, label, cls}`
- `expMatch(candExp, jdExp, jdTitle)` — returns `{match:'yes'/'no'/'unknown', strict: bool}`

**Rendering:**
- `render()` — full re-render based on current hash; also binds upload event listeners
- `cc(c, j)` — renders one candidate card (used in zones view)
- `vSheet(id)` — renders HTML table for sheet view of a JD
- `vQuestions(jid)` — renders editable screening question list

**Excel Downloads:**
- `buildWb(id)` — single JD workbook
- `buildMultiWb()` — multi-JD candidates workbook
- `buildSlWbAll()` — all shortlisted, one sheet per company, JD sub-headers
- `buildSlWbCo(coIdx)` — single company shortlist workbook
- `buildQuestionsWb(jid)` — screening questions workbook

**CV Matching:**
- `matchCvToJds(cvText)` — scores CV against all JDs; **experience is a hard red line** (see §8)
- `handleCvFile(file)` — orchestrates PDF/DOCX/TXT extraction then matching

**Pool Upload:**
- `handlePoolFile(file)` — reads Excel/CSV via SheetJS, maps columns, deduplicates, matches to JDs (experience red line enforced), calls `rebuildCandidateList()`
- `rebuildCandidateList()` — rebuilds `C[]` from `D.pl` and `S.pool`

**Shortlist:**
- `toggleShortlist(cid, companyIdx)` — add/remove from `S.sl`
- `removeFromShortlist(cid)` — explicit remove
- `getShortlistedByCompany()` — returns `{ [coIdx]: { name, jds: { [jdKey]: { title, items[] } } } }`

## 6. State & localStorage

All state is stored under key `"jf"` in `localStorage` as:
```json
{
  "ov": {
    "p42": { "z": "g", "rm": 0, "jd": 7 }
  },
  "log": ["2026-10-21: Jane Doe shortlisted", ...],
  "sl": {
    "p42": { "jd": 7, "co": 2, "ts": 1729503199000, "notes": "Strong candidate" }
  },
  "qe": {
    "7": [{ "cat": "Technical", "q": "Custom question text" }]
  },
  "pool": [
    { "n": "John Smith", "em": "...", "e": "3 years", "_matchedJd": 4, "_matchScore": 2.5, ... }
  ]
}
```

- **`ov`** — per-candidate overrides: zone override (`z`), removed flag (`rm`), reassigned JD (`jd`)
- **`sl`** — shortlisted candidates: jd id, company index, timestamp, HR notes
- **`qe`** — edited screening questions per JD
- **`pool`** — candidates uploaded via the Pool Upload tab (persisted across sessions)

**Important:** State is **per-browser, per-device**. Nothing is synced to the server.

## 7. Scoring System

### 7a. `ingest.py` score (0–100, stored in `data.json`)
| Signal | Max | Logic |
|---|---|---|
| Role/keyword fit | 35 | Jaccard overlap of tokenised JD title vs candidate's skills + designation + qualification |
| Experience | 25 | `25` if in range; penalised linearly for under/over; `8` if unknown |
| Location | 15 | `15` exact city match or remote; `10` open to relocate; `3` mismatch |
| Notice period | 10 | `10` ≤15 days; `8` ≤30; `5` ≤60; `3` ≤90; `1` otherwise |
| Completeness | 15 | CV link (+5), contact (+4), qualification (+3), skills/designation (+3) |

**Hard cap (ingest.py):** If experience is known and outside JD range → score capped at `GREEN-1` (65).

Thresholds: Green ≥ 66, Yellow ≥ 52, Red < 52.

### 7b. Browser-side adjustments in `ai(c, j)`
- If disability criteria not met (no type, or % < 40%) → score is dropped below green threshold
- If experience clearly mismatched → score is dropped below green threshold
- Result is cached on the candidate object; cache key includes JD id

## 8. CV-to-JD Matcher (browser-side)

Located in `vCvMatch()` and `matchCvToJds()`. Runs entirely in the browser — no server call.

### File parsing
- **PDF** → `pdfjs-dist@3.11.174` (CDN lazy-loaded)
- **DOCX/DOC** → `mammoth@1.8.0` (CDN lazy-loaded)
- **TXT** → `TextDecoder`

### Matching pipeline (per JD)
```
1. EXPERIENCE RED LINE (hard gate):
   - Parse CV experience with cvParseExp()
   - Parse JD experience range with parseExpRange()
   - If CV exp is known AND JD has a minimum AND CV exp < minimum - 0.5yr → SKIP JD entirely
   (JD will not appear in results regardless of skill/keyword match)

2. Score remaining JDs on 5 signals (max 100):
   Signal 1: Title keyword match       0–30 pts
   Signal 2: Skill/profile overlap     0–25 pts  (uses candidate skills from existing applicants)
   Signal 3: Domain alignment          0–20 pts  (12 curated domain dictionaries)
   Signal 4: Experience fit            0–15 pts  (only reached if red line passed)
   Signal 5: Qualification match       0–10 pts

3. Sort by total score descending; show top 20
```

### Domain dictionaries (`DOMAIN_SKILLS`)
12 domains: `tech_general`, `data_analytics`, `ai_ml`, `security`, `networking`, `erp_sap`, `finance`, `supply_chain`, `customer_service`, `insurance`, `hr_admin`, `content_moderation`.

### Key helper functions
- `cvParseExp(text)` — regex patterns to extract years from CV text
- `cvParseQual(text)` — returns 0–5 qualification level from CV text
- `jdQualLevel(j)` — returns 0–5 from JD title/experience string
- `jdDomains(j)` — returns array of applicable domain keys for a JD
- `cvToks(text)` — 7-char stem tokeniser (stop words removed)
- `cvFullWords(text)` — full word set for domain skill matching

## 9. Candidate Pool Upload (browser-side)

Located in `vPoolUpload()` and `handlePoolFile()`.

- Accepts `.xlsx`, `.xls`, `.csv` (lazy-loads `xlsx@0.18.5` from CDN)
- Parses first sheet only
- Column headers are normalised (trim + lowercase) and matched against `POOL_COL_MAP` dict (~40 mappings)
- Deduplication by `email+"|"+phone` key
- Each candidate is matched to the **best-fitting JD** using role title + skills keyword overlap (experience red line enforced)
- Saved to `S.pool` in localStorage; `rebuildCandidateList()` merges them into `C[]`
- Pool candidates get `id = "pool_N"`, `sc = 50` (default), `rs = "Pool candidate"`, `pool = true`

### Supported column names (case-insensitive, partial list)
`Name`, `Candidate Name`, `Email`, `Mail Id`, `Phone`, `Mobile`, `Contact No`, `Organization`, `Current Organization`, `Experience`, `Relevant Experience in Years`, `Skills`, `Skillset`, `Disability Type`, `Disability%`, `Location`, `Current Location`, `Role`, `Job Role`, `Qualification`, `Education`, `Current CTC`, `Expected CTC`, `Notice Period`, `Timestamp`, `CV`, `Resume`, `Upload CV`, `Remarks`, `Notes`

```js
  "p42": { jd: 7, co: 2, ts: 1729503199000, notes: "HR note" }

```

### Views
- **`vShortlist()`** groups by company → JD → candidates
- Each company section has individual download button

`Candidate Name`, `Email`, `Phone`, `Current Org`, `Experience`, `Location`, `Qualification`, `Skills`, `Disability Type`, `Disability %`, `Notice Period`, `Expected CTC`, `JD Title`, `Company`, `HR Notes`

Each company is a worksheet; each JD is a merged header row within that sheet.

### Shortlist functions
- `toggleShortlist(cid, coIdx)` — adds with company+JD info, or removes if already there

- `shortlistTo(cid, coIdx, jdId)` — shortlist to a specific company+JD (used for manual reassignment)
- `getShortlistedByCompany()` — groups for rendering and export

## 11. Deployment (Vercel)

1. Push to a **private** GitHub repo (data.json contains candidate PII).
2. In Vercel: **Framework preset = Other** (no build command).
3. Set environment variable `SITE_PASSWORD` → shared with the team.
   - Or `PUBLIC_ACCESS=true` for no password (not recommended: exposes contact details).
4. `api/data.js` is the serverless function: checks `x-password` header, returns `data.json`.
5. `vercel.json` routes `/api/data` to the function and everything else to `public/`.

To refresh candidates: run `ingest.py` locally → commit new `data/data.json` → Vercel auto-deploys.

## 13. Utility Scripts

### `scripts/explore.py`
Prints a human-readable dump of `data/data.json`: company list, all JDs, first 10 people with disability info, multi-JD candidate count. Useful for verifying ingest output.

### `scripts/explore2.py`
Opens `Job Fair Master Sheet.xlsx` and prints all column headers in the "JDs Overview " sheet and the first 10 JD rows. Useful when the master sheet format changes.

### `scripts/fix_scores.py`
One-off patch script (run after ingest if needed). Reads `data.json`, finds any green-zone candidates whose experience is outside the JD range (ingest may have missed edge cases), caps them to `GREEN-1` (65), annotates the reason string with `EXP MISMATCH: Nyrs < required M-Hyrs`, and rewrites `data.json`. Automatically backs up the original to `data.json.backup_original` (only on first run). Prints before/after green counts and a full list of corrections.

## 14. Key Design Decisions & Gotchas

| Topic | Detail |
|---|---|
| **Single-file front-end** | All CSS + JS in `public/index.html` — no build, no bundler, easy to deploy anywhere. ~1500 lines. |
| **No shared state** | HR zone moves, shortlists, notes are localStorage-only. Different team members see different states. |
| **Experience red line (CV matcher)** | If the CV's detected experience is < JD minimum - 0.5yr, the JD is **completely excluded** from CV match results. This is intentional — experience is non-negotiable. |
| **Experience red line (ingest)** | The Python scorer caps scores at `GREEN-1` when experience is outside range. The browser's `ai()` function applies the same cap dynamically for display. |
| **Disability benchmark** | Candidates need a disability type AND ≥40% disability percentage to be "green-eligible" for disability check. The `disCheck()` function enforces this. |
| **Talent pool matching** | Pool candidates (Naukri/Shortlist files) match to up to 5 JDs with score ≥ YELLOW. They are marked with `pool: true` and appear with a "Pool match" badge in the UI. |
| **Uploaded pool (browser)** | Pool candidates uploaded via the UI are stored in `S.pool` in localStorage. They are merged into `C[]` on every `rebuildCandidateList()` call. Their `id` is `"pool_N"` (not `"pN"`). |
| **JD id = array index** | `jds[0].id === 0` always. The `id` field is redundant but included for clarity. `c` is the company index into `cos[]`. |
| **"Not in JD sheet" JDs** | Candidates who applied for roles not found in the master JD sheet get synthetic JDs with `ty: "Not in JD sheet"`. These are skipped in CV matching. |
| **Sheets with trailing space** | The master sheet is named `"JDs Overview "` (trailing space). This is preserved as-is in ingest.py. |
| **Score sort in pl** | `pl` is sorted by `(jid, -score)` so each JD's best candidates come first. The front-end uses this order in sheet view. |
| **ExcelJS** | Used for all `.xlsx` downloads. Lazy-loaded from CDN (`exceljs@4.4.0`). |
| **SheetJS / XLSX** | Used for reading uploaded pool Excel files. Lazy-loaded from CDN (`xlsx@0.18.5`). |
| **PDF.js + Mammoth** | Used for CV text extraction in the browser. Both lazy-loaded from CDN. |
| **Zone override persistence** | `S.ov[cid].z` overrides computed zone. `S.ov[cid].rm = 1` hides the candidate. `S.ov[cid].jd` reassigns to a different JD. |
| **Multi-JD candidates** | `getMultiJdCandidates()` groups `C[]` by normalised email/phone/name and returns people appearing in 2+ JDs. |
